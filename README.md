# 📊 Data Analyst Agent

A production-quality LLM agent that answers natural-language questions about sales data by calling structured tools — with structural read-only SQL enforcement, an 18-question eval suite, and a Streamlit UI.

> **Example:** Ask *"Which region had the biggest drop in sales last quarter?"* and the agent calls `describe_schema()`, writes a SQL query, runs it via `run_sql()`, draws a chart with `make_chart()`, and answers in plain English.

## ★ Key Engineering Decision: Structural Read-Only SQL

> *"Enforce read-only SQL structurally in code (reject anything but SELECT, add a row limit)."*

This is the most important safety feature. Here's why the approach matters:

| Approach | How it works | Can be bypassed? |
|---|---|---|
| **Instructional** | Tell the LLM "only write SELECT" in the system prompt | Yes — LLMs can be jailbroken or hallucinate |
| **Structural** (our approach) | Python validates SQL tokens BEFORE execution | No — Python `if` statements don't lie |

**Two independent enforcement layers** in [`agent/safety.py`](agent/safety.py):

```python
# Layer 1: sqlparse token check
# The first token of any query must be DML type with value "SELECT"
if first_meaningful.ttype is not DML or first_meaningful.normalized.upper() != "SELECT":
    raise SafetyError(f"Only SELECT statements are permitted.")

# Layer 2: regex blacklist (catches multi-statement injections like "SELECT 1; DROP TABLE")
if _BANNED_KEYWORDS.search(query):
    raise SafetyError(f"Banned keyword '{match.group()}' detected.")

# Layer 3: Row cap (protects context window and latency)
query = f"{query} LIMIT {max_rows}"   # appended if no LIMIT present
```

## Failures I Found and How I Fixed Them

### 1. Wrong column name: `subcategory` vs `sub_category`

**Symptom:** Agent wrote `SELECT sub_category ...` but the actual column was `subcategory`, causing a SQL error.

**Root cause:** The LLM guessed column names instead of calling `describe_schema()` first.

**Fix:** Added an explicit instruction in the system prompt: *"Call `describe_schema()` FIRST before writing any SQL."* Also updated `describe_schema()` to show exact column names with underscores so the LLM copies them correctly.

---

### 2. Quarter filter was wrong (months 1–3 for Q1, but LLM wrote `BETWEEN '01' AND '03'` with string comparison)

**Symptom:** `strftime('%m', order_date) BETWEEN '01' AND '03'` works fine, but the LLM sometimes wrote `BETWEEN '1' AND '3'` (single digit). SQLite compares these lexicographically, so month `'10'` falls between `'1'` and `'3'` alphabetically.

**Root cause:** Inconsistent zero-padding in string comparison.

**Fix:** Added a SQL pattern to the system prompt using `CAST(strftime('%m', ...) AS INTEGER)` for numeric comparison. Example:
```sql
CAST(strftime('%m', order_date) AS INTEGER) BETWEEN 10 AND 12
```

---

### 3. `make_chart()` crashed when LLM passed `values` as strings instead of floats

**Symptom:** `TypeError: '<' not supported between instances of 'str' and 'float'` when matplotlib tried to plot.

**Root cause:** The LLM extracted numbers from SQL results and passed them as `["1234.56", "987.00"]` (JSON strings, not numbers), because the tool schema said `"type": "number"` but the LLM used query string formatting.

**Fix:** Added defensive casting in `make_chart()`:
```python
values = [float(v) for v in values]   # coerce strings to float
```

---

### 4. Multi-statement injection attempt wasn't caught by sqlparse alone

**Symptom:** `SELECT 1; DROP TABLE sales` — sqlparse returned two parsed statements but didn't raise an error.

**Root cause:** We only checked the first parsed statement's type; the second (DROP) was ignored.

**Fix:** Added an explicit check:
```python
if len(parsed) > 1:
    raise SafetyError("Multiple statements detected. Only a single SELECT is allowed.")
```
This, combined with the regex blacklist, makes multi-statement injection impossible.

---

### 5. Agent loop could spin forever on API errors

**Symptom:** Transient OpenAI API 429 (rate limit) errors caused the agent to retry indefinitely.

**Root cause:** The loop only had a `MAX_ITERATIONS` check but didn't handle exceptions.

**Fix:** Wrapped the API call in a `try/except` and added a `MAX_ITERATIONS = 10` hard cap. Any unrecoverable error returns a structured error response instead of looping.
